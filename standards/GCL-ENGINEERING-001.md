## Obligation

The implementation agent is responsible for architecture, necessity, code quality, validation, operations, rollback, and retirement; the Human Steward should not be required to identify duplicate infrastructure or catch engineering architecture mistakes. Agents must give clear evidence-backed judgments and favor the smallest dependable solution.

1. **Reuse first.** Inventory existing GitHub, repository, and runtime functions before proposing a new database, worker, service, supervisor, queue, protocol, or abstraction. The default is *do not add*.
2. **One authority per kind of state.** GitHub repository artifacts, protected commits, PRs, Issues, Actions, checks, and evidence records own governed work and admission under existing programme rules. Projects are indexes, not an independent source of truth. AETHER continues to own production semantic authority; MATHCERT alone governs mathematical certification.
3. **Local persistence is an exception, not a second workflow.** Keep only execution-local confidential, atomic, offline, or in-flight evidence where GitHub cannot safely replace it. For every local database or ledger record owner, unique purpose, readers/writers, precedence, failure behavior, custody, reconciliation, and sunset. Preserve incomplete effects before retirement.
4. **Diagnostics must not become speculative architecture.** Identify the failing boundary with reproducible evidence. Distinguish request execution, response emission, caller delivery, protected admission and external effects. Fix the smallest demonstrated cause rather than adding speculative recovery machinery.
5. **Safety and governance remain intact.** Do not replay uncertain non-idempotent effects; reconcile exact identities first. Fail closed on authority, admissions, safety controls, and unsupported claims, but continue authorized evidence recovery.
6. **Completion includes actual operation.** Source tests and CI are not deployment. Protected merge is not live activation. A healthy endpoint is not a caller-visible result. Prove exact deployed source, legitimate reviews, required end-to-end behavior, rollback and steady-state operation before reporting completion.
7. **No abandoned integration.** When adopting a shared engineering rule, inventory all affected repositories and entrypoints; record explicit adoption or a specific exception for each. Do not claim organization-wide reach from a change to one repository.
8. **Decision clarity.** Report verified observations, hypotheses, actions performed, test and deployment evidence, remaining obligations and exactly named boundaries. Avoid speculative certainty and elaborate new process layers.
9. **Stabilization outranks expansion.** When reliability is not established, defer discretionary infrastructure additions and prioritize a narrow, measured acceptance gate. Do not weaken independent programme research or existing governance merely because an infrastructure subsystem is degraded.

## Minimal review check

For any substantive infrastructure change, the PR must explain in proportion to its complexity: the existing capability inspected, demonstrated gap, smallest design, duplicate-state and authority assessment, failure modes, acceptance evidence, and rollback/retirement. For a simple repair, the PR body may supply this in a few sentences. No new meeting, supervisor, or generic Steward-approval step is required.

## Adoption and closure

The repository's protected AGENTS.md (or equivalent authority-bearing entrypoint) must pin the exact admitted revision and bind the affected agents to this standard, while preserving superior and specialty policies. The shared adoption register must distinguish candidate, protected-admitted, adopted, and verified state for every targeted repository; report exceptions and outstanding work rather than silently narrowing scope.

This standard does not itself alter constitutional powers, certification standards, repository branch protection, or credentials.
